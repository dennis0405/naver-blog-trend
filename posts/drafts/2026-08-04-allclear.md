# 애플 개발자 계정 이전, Sign in with Apple 사용자 식별자까지 옮긴 과정

## 한 줄 요약

Sign in with Apple을 사용하는 앱의 계정 이전은 App Store Connect에서 소유권을 넘기는 것으로 끝나지 않는다. 이전 전에는 기존 사용자 식별자를 `transfer_identifier`로 바꾸고, 이전 후에는 이를 새 팀의 `sub`로 다시 바꿔야 한다. 앱 쪽에서도 Team ID, provisioning profile, entitlement를 새 계정 기준으로 재구성해야 한다.

## 문제 상황

운영 중인 iOS 앱의 소유권을 기존 Apple Developer 계정에서 새 계정으로 이전해야 했다.

처음에는 App Store Connect에서 이전 요청을 보내고, Xcode의 Team만 새 계정으로 바꾸면 끝날 것이라고 생각했다. Bundle ID가 그대로 유지되니 사용자 입장에서도 별다른 변화가 없을 것으로 봤다.

하지만 이 앱은 Sign in with Apple을 사용하고 있었다. Apple 로그인에서 발급되는 사용자 식별자 `sub`는 앱에만 종속된 값이 아니라 개발자 팀에도 종속된다. 앱의 소유 팀이 바뀌면 같은 사용자가 로그인하더라도 새 팀 기준의 `sub`가 발급된다.

당시 서버는 Apple의 `sub`를 계정의 고유 식별자로 사용하고 있었다. 아무 준비 없이 이전하면 기존 사용자가 새 사용자로 인식되어 중복 계정이 만들어질 수 있었다.

문제는 두 갈래였다.

1. 기존 Apple 로그인 사용자를 새 팀의 사용자 식별자로 안전하게 옮겨야 했다.
2. iOS 프로젝트의 서명 설정과 capability를 새 개발자 계정에 맞게 바꿔야 했다.

이 글에서는 실제로 어떤 순서로 작업했는지, 어떤 배치를 실행했는지, 중간에 어떤 오류를 만났는지를 정리한다.

## 처음 세운 가설

처음에는 다음 순서면 충분하다고 생각했다.

1. 기존 계정에서 앱 이전 요청
2. 새 계정에서 이전 수락
3. Xcode의 Team ID와 provisioning profile 변경
4. 새 빌드 배포

이 순서는 Sign in with Apple을 사용하지 않는 단순한 앱이라면 큰 틀에서 맞을 수 있다. 하지만 Apple 로그인을 사용하면 가장 중요한 작업이 이전 요청보다 앞에 와야 한다.

기존 사용자의 `old_sub`를 새 팀과 연결할 중간 식별자로 바꾸지 않은 채 앱부터 넘기면, 이후 기존 사용자와 새 `sub`를 연결할 근거가 사라질 수 있기 때문이다.

실제로 필요한 흐름은 다음과 같았다.

```text
기존 팀의 old_sub
  -> 이전용 transfer_identifier 생성
  -> App Store Connect에서 앱 이전
  -> 새 팀의 new_sub로 교환
  -> DB의 로그인 식별자 갱신
```

`transfer_identifier`는 우리가 임의로 만드는 값이 아니다. 기존 팀의 인증 정보로 Apple의 migration API를 호출하면 Apple이 사용자별로 반환하는, 이전 절차에만 쓰이는 안정적인 연결 값이다.

## 실제로 진행한 전체 순서

작업은 크게 이전 전, 실제 이전, 이전 후의 세 단계로 나눴다.

### 1. 이전 대상과 capability를 먼저 조사했다

가장 먼저 확인한 것은 Bundle ID 자체보다 이 앱이 어떤 Apple capability를 사용하고 있는지였다.

- Sign in with Apple
- App Groups
- Push Notifications
- Keychain Sharing 사용 여부
- App ID와 Services ID의 연결 관계
- 각 빌드 configuration이 사용하는 Bundle ID
- 기존 Team ID와 새 Team ID

Apple 공식 문서에 따르면 Sign in with Apple 앱이 그룹으로 묶여 있다면 이전 전에 그룹을 해제해야 한다. App Groups는 앱과 함께 자동으로 이전되지 않으며, Keychain Sharing은 앱 업데이트 시 새 팀 기준으로 다시 구성해야 할 수 있다.

따라서 “Bundle ID가 유지된다”와 “기존 서명 설정을 그대로 쓸 수 있다”는 전혀 다른 이야기였다.

### 2. 이전에 필요한 정보를 양쪽 계정에서 확보했다

이전용 API를 호출하려면 `.p8` 파일만 있어서는 안 된다. 발신 팀과 수신 팀의 정보를 나눠서 준비해야 했다.

| 구분 | 준비한 정보 |
|---|---|
| 기존 팀 | Team ID, Sign in with Apple Key ID, `.p8`, 앱 grouping 상태 |
| 새 팀 | Team ID, Sign in with Apple Key ID, `.p8` |
| 앱 | production Bundle ID, App ID·Services ID 관계, 사용 중인 capability |
| App Store Connect | 수신 계정의 Account Holder 이메일 |

기존 개발사에서 인증 정보를 받아야 한다면 raw `.p8`를 전달받는 것보다 기존 개발사가 사용자별 `transfer_identifier`를 추출해 CSV로 전달하는 방식이 더 안전하다. 직접 키를 받아 실행해야 한다면 `.p8`는 저장소에 넣지 않고 로컬의 제한된 경로나 secret manager에서만 읽어야 한다.

### 3. 기존 Apple 로그인 사용자를 inventory로 추출했다

서버에서는 Apple 사용자의 `sub`를 계정 테이블의 사용자명 필드에 저장하고 있었다. 먼저 이전 대상 전체를 CSV로 백업했다.

초기에는 계정과 사용자 테이블을 모두 `INNER JOIN`한 쿼리를 사용했다.

```sql
SELECT
  a.id AS account_id,
  a.username AS old_sub,
  au.user_id,
  u.email
FROM account a
JOIN account_user au ON au.account_id = a.id
JOIN "user" u ON u.id = au.user_id
WHERE a.type = 'apple';
```

그런데 Apple 계정 행은 존재하는데 결과가 나오지 않는 경우가 있었다. 원인은 조회 컬럼이 아니라 `JOIN`이었다. 일부 행은 연결 상태나 탈퇴 상태 때문에 중간 테이블에서 탈락하고 있었다.

마이그레이션 inventory의 목적은 정상 사용자만 보는 것이 아니라 이전 대상 전체를 빠짐없이 확인하는 것이다. 그래서 연결 테이블을 `LEFT JOIN`으로 바꾸고, 연결이 끊긴 행도 결과에 남도록 했다.

추출 후에는 다음을 확인했다.

- Apple 계정 총수와 활성·탈퇴 계정 합계가 일치하는가
- `old_sub`가 중복되지 않는가
- 계정 연결이 누락된 행이 있는가
- CSV 백업의 행 수와 DB 조회 결과가 일치하는가

정확한 내부 계정 수는 공개하지 않지만, 중복된 `old_sub`는 없었고 이전 대상을 확정할 수 있었다.

### 4. 마이그레이션 상태를 별도 테이블로 관리했다

기존 `account` 테이블을 바로 수정하지 않았다. 사용자별 진행 상태를 추적할 별도 테이블을 만들었다.

배치에 앞서 `account.username`의 길이도 넉넉하게 늘렸다. 기존 `sub`와 새 `sub`의 길이가 항상 같다고 가정하면 전환 시 저장 단계에서 실패할 수 있기 때문이다.

```text
apple_account_migration
  - account_id
  - app_bundle_id
  - source_team_id
  - target_team_id
  - old_sub
  - transfer_identifier
  - new_sub
  - status
  - last_error
  - transfer_identifier_collected_at
  - new_sub_collected_at
  - migrated_at
```

상태는 다음처럼 나눴다.

```text
pending
transfer_identifier_collected
new_sub_collected
migrated
failed
```

`account_id`, `old_sub`, `transfer_identifier`, `new_sub`에는 unique index를 걸었다. 배치를 재실행하더라도 같은 사용자를 중복 처리하거나 서로 다른 계정에 같은 식별자를 넣지 못하게 하기 위해서였다.

마이그레이션 대상은 기존 Apple 계정에서 채웠다.

```sql
INSERT INTO apple_account_migration (
  account_id,
  app_bundle_id,
  source_team_id,
  target_team_id,
  old_sub,
  status
)
SELECT
  id,
  '<APP_BUNDLE_ID>',
  '<SOURCE_TEAM_ID>',
  '<TARGET_TEAM_ID>',
  username,
  'pending'
FROM account
WHERE type = 'apple';
```

### 5. 이전 전 `old_sub -> transfer_identifier` 배치를 실행했다

기존 팀의 Team ID, Sign in with Apple Key ID, `.p8` private key를 이용해 client secret JWT를 만들었다. 그다음 Apple의 토큰 API에서 `user.migration` scope의 access token을 발급받았다.

```text
POST https://appleid.apple.com/auth/token

grant_type=client_credentials
scope=user.migration
client_id=<APP_ID_OR_SERVICES_ID>
client_secret=<SOURCE_TEAM_CLIENT_SECRET>
```

발급받은 access token으로 사용자마다 `userMigrationInfo` API를 호출했다.

```text
POST https://appleid.apple.com/auth/usermigrationinfo

sub=<OLD_SUB>
target=<TARGET_TEAM_ID>
client_id=<APP_ID_OR_SERVICES_ID>
client_secret=<SOURCE_TEAM_CLIENT_SECRET>
```

응답의 `transfer_sub`를 `apple_account_migration.transfer_identifier`에 저장하고 상태를 `transfer_identifier_collected`로 변경했다.

이 배치는 로컬에서 실행하되 Telepresence로 운영 DB에 연결했다. 앱 서버에 일회성 migration credential을 상시 배포하지 않기 위해서였다. 실행 전에 현재 database와 schema, 대상 행 수를 확인하고, 스크립트와 키 파일은 커밋하지 않았다.

처음에는 한 명씩 순차 호출하고 요청 사이에 고정 지연을 넣었다. 안전하긴 했지만 전체 작업이 지나치게 느렸다. 이후 다음 방식으로 바꿨다.

- 이미 성공한 행은 다시 조회하지 않음
- 처리 단위를 batch로 가져옴
- 제한된 수의 worker로 병렬 처리
- 실패 시 정해진 횟수만 재시도
- `User not found`처럼 재시도로 해결되지 않는 오류는 별도 보관

속도를 높인 뒤에도 무제한 병렬 호출은 하지 않았다. Apple의 rate limit에 걸리면 동시 실행 수를 낮출 수 있도록 concurrency와 요청 간격을 설정값으로 분리했다.

대부분의 사용자는 정상적으로 `transfer_identifier`를 받았다. 소수 사용자는 다음과 같은 응답으로 실패했다.

```text
400 invalid_request
User not found.
```

이 행들은 반복해서 호출해도 결과가 달라지지 않았다. 성공한 사용자와 분리해 `failed` 상태와 오류 내용을 보관하고, 실패 목록을 별도 백업한 뒤 이전을 진행했다.

초기 스크립트의 성공 로그에는 식별자를 그대로 출력할 여지가 있었다. 일회성 로컬 실행이었지만 좋은 방식은 아니었다. 운영용으로 다시 만든다면 `old_sub`, `new_sub`, 이메일, client secret은 출력하지 않고 account ID와 마스킹한 fingerprint, 처리 상태만 남기는 편이 안전하다.

### 6. 앱 이전 전에 로그인 fallback을 먼저 배포했다

앱을 먼저 이전하고 서버를 나중에 수정하면 그 사이 로그인한 기존 사용자가 새 계정으로 만들어질 수 있다. 그래서 서버 코드를 먼저 배포했다.

이전 후 Apple의 ID token에는 새 팀 기준 `sub`와 함께 일정 기간 `transfer_sub`가 들어올 수 있다. 서버는 다음 순서로 사용자를 찾도록 변경했다.

```text
1. 새 sub로 기존 계정 조회
2. 없고 transfer_sub가 있으면 migration 테이블 조회
3. transfer_identifier 또는 old_sub가 일치하는 기존 계정 조회
4. 기존 계정의 식별자를 새 sub로 갱신
5. migration 상태를 migrated로 변경
6. 그래도 찾지 못하면 신규 사용자 생성
```

이 로직은 전체 배치가 끝나기 전 로그인하는 사용자를 위한 안전망이었다. 정상 경로를 영구히 복잡하게 만들기 위한 코드가 아니었기 때문에, 마이그레이션 완료 후 제거할 수 있도록 별도 코드로 관리했다.

### 7. App Store Connect에서 실제 앱 이전을 진행했다

이전 전 준비를 마친 다음에야 App Store Connect의 앱 이전을 진행했다.

1. 기존 계정의 Account Holder가 앱 이전 요청
2. 새 계정의 Account Holder가 이전 수락
3. 이전 완료 상태 확인
4. 새 팀에서 App ID와 Sign in with Apple capability 확인
5. 새 팀 기준 Sign in with Apple key와 provisioning profile 생성

이때 production Bundle ID는 바꾸지 않았다. App Store에 올라간 동일 앱으로 이어지려면 기존 Bundle ID를 유지해야 한다. 바뀐 것은 Bundle ID 그 자체보다 그 Identifier를 소유하고 서명하는 팀이었다.

이전 후에는 App ID와 capability만 보지 않고 앱 메타데이터, 연락처, 개인정보처리방침 URL, 구독 관련 설정처럼 App Store Connect에 남아 있는 운영 정보도 별도 체크리스트로 확인했다. 앱 이전과 서명 이전은 한 번에 끝나는 단일 작업이 아니었다.

### 8. 이전 후 `transfer_identifier -> new_sub` 배치를 실행했다

처음에는 서버의 Team ID와 Key ID 같은 운영 환경 변수도 새 팀 값으로 바꿔야 한다고 생각했다. 실제 로그인 callback 경로를 다시 확인해 보니 런타임 서버는 클라이언트가 보낸 ID token을 검증할 뿐, migration용 Team ID·Key ID·`.p8`를 사용하지 않았다. 이 credential은 이전 전후 일회성 배치에만 필요했다. 사용처를 확인하지 않고 운영 환경 변수를 바꾸지 않은 것이 오히려 안전했다.

이전이 끝난 뒤에는 새 팀의 Team ID, Key ID, `.p8`로 client secret을 다시 만들었다.

토큰 발급 방식은 같지만 이번 client secret은 수신 팀 기준이다. 그다음 `userMigrationInfo`에는 기존 `sub`가 아니라 이전 전에 저장한 `transfer_sub`를 전달했다.

```text
POST https://appleid.apple.com/auth/usermigrationinfo

transfer_sub=<TRANSFER_IDENTIFIER>
client_id=<APP_ID_OR_SERVICES_ID>
client_secret=<TARGET_TEAM_CLIENT_SECRET>
```

응답으로 받은 값은 새 팀에 종속된 사용자 식별자 `sub`였다. 이를 migration 테이블의 `new_sub`에 먼저 저장했다.

바로 `account.username`을 바꾸지 않고 두 개의 스크립트로 나눈 이유는 검증 지점을 만들기 위해서였다.

1. `collect-new-sub`: `transfer_identifier -> new_sub`를 수집하고 상태를 `new_sub_collected`로 변경
2. 중복·누락·실패 건수 검증
3. `apply-new-sub`: 검증을 통과한 행만 `account.username` 갱신
4. 실제로 한 행이 변경됐을 때만 상태를 `migrated`로 변경

DB 반영 배치에는 현재 값이 여전히 `old_sub`인지를 확인하는 조건을 넣었다.

```sql
UPDATE account
SET username = :new_sub,
    updated_at = CURRENT_TIMESTAMP
WHERE id = :account_id
  AND type = 'apple'
  AND username = :old_sub;
```

이미 다른 경로에서 식별자가 바뀌었거나 예상하지 못한 값이 들어 있다면 덮어쓰지 않고 실패로 남기는 compare-and-set 형태다. 소량 샘플을 먼저 실행해 Apple 응답과 DB 상태를 확인한 뒤 전체 배치를 실행했다.

Apple은 수신 팀이 이전 수락 후 60일 이내에 식별자 교환을 끝내도록 안내한다. 이 기간에는 로그인 ID token에도 `transfer_sub`가 포함될 수 있지만, 60일이 지나면 API와 token의 이전 정보에 더는 의존할 수 없다. 이 60일은 fallback 코드를 반드시 유지해야 하는 기간이 아니라 식별자를 교환할 수 있는 최대 기한이다. 이번에는 전체 배치와 로그인 검증을 빠르게 끝낸 뒤 임시 fallback을 제거했다.

### 9. iOS Identifier와 서명 설정을 새 팀 기준으로 바꿨다

서버의 사용자 마이그레이션과 별개로 iOS 프로젝트도 새 계정에 맞게 재구성했다.

실제 변경의 핵심은 다음과 같았다.

- 모든 iOS configuration의 Development Team을 새 팀으로 변경
- Release와 개발용 provisioning profile을 새 팀에서 다시 생성
- Release와 Staging은 이전된 production Bundle ID 유지
- Debug와 Local은 새 팀에 등록한 개발용 Bundle ID로 통일
- configuration별 entitlement 파일 분리
- 이전 팀의 App Group 참조 제거
- Debug와 Local entitlement에도 Sign in with Apple capability 추가
- 수동 서명 설정에서 configuration별 profile을 명시

설정은 다음과 같은 형태가 됐다.

```text
Release / Staging
  PRODUCT_BUNDLE_IDENTIFIER = <PRODUCTION_BUNDLE_ID>
  DEVELOPMENT_TEAM = <NEW_TEAM_ID>
  PROVISIONING_PROFILE_SPECIFIER = <NEW_RELEASE_PROFILE>

Debug / Local
  PRODUCT_BUNDLE_IDENTIFIER = <DEVELOPMENT_BUNDLE_ID>
  DEVELOPMENT_TEAM = <NEW_TEAM_ID>
  PROVISIONING_PROFILE_SPECIFIER = <NEW_DEVELOPMENT_PROFILE>
```

entitlement도 configuration별로 분리했다.

```xml
<key>com.apple.developer.applesignin</key>
<array>
  <string>Default</string>
</array>
```

기존에는 여러 configuration이 같은 entitlement를 공유하면서 이전 팀의 App Group을 참조하고 있었다. 새 팀에서 존재하지 않는 group을 계속 요청하면 profile과 entitlement가 일치하지 않아 서명 오류가 날 수 있다. 사용하지 않는 이전 팀의 group을 제거하고, 실제 필요한 capability만 configuration별로 맞췄다.

### 10. 시뮬레이터의 Apple 로그인 오류도 함께 정리했다

앱 코드에는 로그인 요청 후 `getCredentialStateForUser()`로 상태를 한 번 더 확인하는 로직이 있었다. 이 호출은 iOS 시뮬레이터에서 오류를 일으켜 새 서명 설정을 검증하기 어렵게 만들었다.

로그인 요청에서 `identityToken`을 정상적으로 받았는지 확인한 뒤 서버 callback으로 넘기도록 흐름을 단순화했다.

```ts
const response = await appleAuth.performRequest({
  requestedOperation: appleAuth.Operation.LOGIN,
  requestedScopes: [appleAuth.Scope.FULL_NAME, appleAuth.Scope.EMAIL],
})

if (!response.identityToken) {
  return
}

await authService.callback(AuthProvider.APPLE, response.identityToken)
```

이 변경으로 시뮬레이터에서 credential state 조회 때문에 로그인 흐름이 끊기는 문제를 분리할 수 있었다. 실제 인증의 유효성 검사는 서버에서 token 검증을 기준으로 수행해야 한다.

## 실패한 접근

### 앱 이전을 먼저 하려 했다

가장 위험했던 가설은 “App Store Connect 이전부터 하고 사용자 migration은 나중에 처리해도 된다”는 것이었다.

Apple 로그인 사용자의 `sub`가 팀에 종속된다는 사실을 확인한 뒤 순서를 바꿨다. 이전 전 `transfer_identifier` 수집과 서버 fallback 배포가 먼저였다.

### 정상 연결된 사용자만 inventory에 포함하려 했다

`INNER JOIN`으로 추출한 inventory는 연결이 끊기거나 탈퇴 처리된 계정을 놓칠 수 있었다. 마이그레이션은 현재 화면에 노출되는 사용자 목록이 아니라 인증 계정 전체를 대상으로 해야 했다. `LEFT JOIN`과 별도 검증 쿼리로 바꿨다.

### 배치에서 dev DB에 연결했다

로컬에서 Telepresence를 사용하던 중 배치가 잘못된 환경의 DB 서비스에 연결됐다.

```text
relation "apple_account_migration" does not exist
```

처음에는 schema 문제라고 생각했지만 `current_database()`, `current_schema()`, Apple 계정 수를 함께 확인하면서 접속 대상이 잘못됐다는 것을 찾았다. 배치 시작 시 DB 이름, schema, 대상 행 수를 출력하도록 바꾸고 올바른 환경에서 다시 실행했다.

### 이전 후 토큰 발급에서 `invalid_client`가 발생했다

새 팀 credential로 `user.migration` access token을 요청했지만 다음 오류가 발생했다.

```text
400 {"error":"invalid_client"}
```

처음에는 client secret 생성 코드가 잘못됐다고 생각했다. 그래서 민감한 원문을 출력하지 않는 범위에서 다음을 확인했다.

- JWT header의 `alg`, `kid`
- payload의 `iss`, `sub`, `aud`, `iat`, `exp`
- private key fingerprint
- client secret hash와 길이
- Apple 응답 header
- App ID의 Sign in with Apple 활성화 여부
- key가 연결된 Primary App ID
- `client_id`가 Bundle ID인지 Services ID인지

JWT 구조를 확인한 뒤 Apple Developer 포털에서 App ID의 Sign in with Apple 설정과 key 연결 값을 다시 적용하고 재시도했다. 그러자 같은 코드로 access token 발급에 성공했고, 사용자 식별자 교환과 DB 갱신을 이어갈 수 있었다.

Apple 내부 원인을 직접 확인할 수는 없었기 때문에 “단순 반영 지연이었다”거나 “특정 설정 하나가 틀렸다”고 단정하지 않았다. 확인 가능한 사실은 JWT 코드를 바꾸지 않은 상태에서 포털 설정을 다시 적용한 뒤 성공했다는 점이다. 그래서 이 오류의 해결 기록도 추측이 아니라 재현 가능한 확인 순서로 남겼다.

## 실제 원인

이번 작업에서 문제의 핵심은 하나의 설정 오류가 아니었다. 앱 이전에 포함된 식별자의 범위를 너무 좁게 본 것이 근본 원인이었다.

Apple 앱에는 서로 다른 수명의 식별자가 함께 있다.

| 구분 | 이전 시 처리 |
|---|---|
| App Store의 Bundle ID | 기존 production 값을 유지 |
| Development Team | 새 팀으로 변경 |
| Provisioning profile | 새 팀에서 재생성 |
| App Group | 자동 이전되지 않으므로 재등록 또는 제거 |
| Apple 로그인 `sub` | 팀 종속 값이므로 사용자별 migration 필요 |
| `transfer_identifier` | 이전 팀과 새 팀의 `sub`를 잇는 임시 식별자 |

즉 App Store에 보이는 앱의 Bundle ID가 같다고 해서 인증과 서명에 쓰이는 모든 식별자가 유지되는 것은 아니었다.

## 해결 방법

최종적으로 사용한 순서를 다시 정리하면 다음과 같다.

### 이전 전

1. App Store Connect의 이전 가능 조건 확인
2. Sign in with Apple grouping과 Services ID 관계 확인
3. 기존 팀의 Team ID·Key ID·`.p8`와 수신 Account Holder 정보 확보
4. Apple 로그인 계정 전체 inventory와 CSV 백업 생성
5. 계정 식별자 컬럼 길이와 migration 테이블·unique index 준비
6. 기존 팀 credential로 `old_sub -> transfer_identifier` 배치 실행
7. 실패 행과 오류 원인 별도 백업
8. 로그인 callback에 `transfer_sub` fallback 구현
9. fallback 서버 코드를 production에 먼저 배포

### 실제 이전

1. 기존 Account Holder가 앱 이전 요청
2. 새 Account Holder가 요청 수락
3. 이전 완료 상태 확인
4. 새 팀의 App ID, capability, Sign in with Apple key 확인
5. provisioning profile 재생성과 App Store Connect 운영 정보 확인

### 이전 후

1. 런타임과 배치의 credential 사용처를 구분
2. 새 팀 credential로 access token 발급
3. `collect-new-sub`를 소량 실행해 `new_sub` 수집
4. 중복, 누락, 실패 여부 검증 후 전체 수집 배치 실행
5. 별도 `apply-new-sub` 배치로 `account.username` 갱신
6. 계정 값이 `old_sub`와 일치하는 행만 변경됐는지 검증
7. 기존 사용자와 신규 사용자의 Apple 로그인 smoke test
8. 새 팀 기준 iOS Team, profile, entitlement 적용
9. 모든 사용자 migration 완료 후 임시 fallback 코드와 일회성 스크립트 제거

## 결과

마이그레이션 가능한 Apple 계정의 식별자를 새 팀 기준 `sub`로 변경했다. 정확한 내부 수치는 공개하지 않지만, 이전 전에 따로 보관한 소수 실패 행을 제외한 대상은 모두 `old_sub -> transfer_identifier -> new_sub` 순서로 전환했다.

완료 여부는 다음 조건으로 검증했다.

- `pending` 상태가 남지 않음
- 성공 행의 `transfer_identifier`와 `new_sub`가 모두 채워짐
- `new_sub` 중복이 없음
- 계정 테이블의 식별자와 migration 테이블의 `new_sub`가 일치함
- 기존 Apple 사용자가 중복 계정 없이 로그인됨
- 신규 Apple 사용자도 정상 가입됨

전체 사용자 식별자 전환이 끝난 뒤에는 로그인 callback의 `transfer_sub` 임시 처리, 서버 코드의 migration 엔티티, 일회성 스크립트를 제거했다. 일시적인 이전 로직을 정상 로그인 경로에 계속 남겨 두지 않은 것도 중요한 마무리 작업이었다.

다만 운영 DB의 migration 테이블은 곧바로 삭제하지 않았다. 전환 결과와 실패 내역을 확인할 감사 자료로 당분간 남겼다. 코드 정리와 데이터 삭제는 같은 작업이 아니므로, 보존 기간과 삭제 시점을 정한 뒤 별도로 처리해야 한다.

iOS 쪽에서는 production Bundle ID를 유지하면서 새 팀의 provisioning profile로 서명하도록 바꿨다. Debug와 Local configuration은 새 계정에 등록된 개발용 Identifier를 사용하고, 각각 필요한 Sign in with Apple entitlement를 갖도록 정리했다.

## 배운 점

### App Transfer는 소유권 이전이 아니라 식별자 전환 작업이다

App Store Connect 화면만 보면 앱 하나를 다른 계정으로 넘기는 일처럼 보인다. 실제로는 사용자 식별자, 서명 주체, profile, capability의 소유권을 함께 옮기는 작업이다.

### 이전 전 작업이 더 중요하다

`transfer_identifier`와 fallback 서버 코드가 준비되지 않은 상태에서 앱부터 넘기면 복구가 훨씬 어려워진다. 마이그레이션에서는 “무엇을 바꿀지”만큼 “언제 바꿀지”가 중요했다.

### 배치는 반드시 재실행 가능해야 한다

외부 API를 사용자 수만큼 호출하는 작업은 중간에 실패할 수밖에 없다. 성공한 행을 건너뛰고, 실패 이유를 보관하고, 일부만 다시 실행할 수 있어야 운영 중 멈췄다가 안전하게 이어갈 수 있다.

### 환경 이름을 로그에 남겨야 한다

dev와 production의 서비스 이름이 비슷하면 사람은 쉽게 잘못 연결한다. 배치 시작 로그에 DB host를 그대로 노출할 필요는 없지만, 환경명, database, schema, 대상 행 수는 반드시 남기는 편이 좋다.

### `invalid_client`는 확인 순서가 중요하다

`invalid_client`가 난다고 곧바로 JWT 생성 코드의 문제라고 볼 수는 없다. JWT claim과 key fingerprint를 먼저 확인하고, App ID, Services ID, Primary App ID, key 연결 상태를 포털에서 다시 확인·적용하는 순서가 유용했다. 이번에는 포털 설정을 재적용한 뒤 같은 코드가 성공했지만 Apple 내부 원인까지 확인한 것은 아니므로 그 이상은 단정하지 않았다.

### 60일은 유예 기간이지 작업 일정이 아니다

Apple이 안내하는 60일은 사용자 식별자를 교환할 수 있는 최대 기한이다. fallback을 60일 내내 유지해야 한다는 뜻은 아니다. 배치와 검증을 일찍 끝낼 수 있다면 임시 로그인 분기를 빠르게 제거하는 편이 정상 경로를 단순하게 유지하는 데 도움이 된다.

### 일회성 스크립트도 secret과 로그를 다뤄야 한다

로컬에서 한 번만 돌리는 코드라도 `.p8`, DB credential, 사용자 식별자를 코드나 로그에 그대로 남기면 안 된다. 이번 스크립트는 커밋하지 않고 실행 후 삭제했지만, 다시 설계한다면 환경 변수나 secret manager를 사용하고 로그에는 마스킹된 식별자만 남길 것이다.
